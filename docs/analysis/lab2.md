# Порівняльний аналіз архітектури

## 1. Що змінилося в структурі проєкту порівняно з лабораторною 1?

У першій лабораторній роботі проєкт мав просту плоску структуру: контролер викликав сервіс, сервіс напряму працював із TypeORM-репозиторієм. Валідація відбувалась лише через DTO з `class-validator`, бізнес-логіка була змішана з інфраструктурним кодом, а помилки повертались як HTTP-виключення прямо із сервісу.

Починаючи з другої лабораторної проєкт було перебудовано за принципами **Clean Architecture** і далі поглиблено у третій. Кожен модуль тепер містить чітко визначені відповідальності:

| Елемент | Лаб. 1 | Лаб. 2–3 |
|---------|--------|----------|
| Структура модуля | `controller` + `service` + `entity` | + `factory`, `errors`, `dto`, `guard`, `enum`, `domain`, `repository/` |
| Валідація | Лише DTO (`class-validator`) | DTO + Domain Factory (бізнес-інваріанти) |
| Обробка помилок | `throw new HttpException(...)` у сервісах | `DomainError` → `DomainExceptionFilter` |
| Авторизація | Відсутня або базова | `JwtAuthGuard` + `MemberGuard` з рольовою моделлю |
| Доменна модель | TypeORM entity = доменний об'єкт | Окремі domain-класи з маппінгом із БД |
| Доступ до БД | `Repository<T>` безпосередньо в сервісі | Шар `*Repository` над TypeORM |

Ключові структурні зміни:

**Шар фабрик** (`UserFactory`, `ChatFactory`, `MemberFactory`, `MessageFactory`) — чистий TypeScript без залежностей від фреймворку, відповідає за валідацію інваріантів і початкове конструювання об'єктів.

**Ієрархія доменних помилок** (`DomainError` → конкретні помилки з `statusCode`) — дозволяє сервісам кидати семантичні помилки без знання про HTTP.

**Шар репозиторіїв** (`ChatRepository`, `MemberRepository` тощо) — надстройка над TypeORM, що повертає domain-моделі замість entity. Сервіс більше не знає про `@InjectRepository`, `findOne`, `findAndCount`.

**Domain-класи з поведінкою** — `MemberDomain` і `MessageDomain` є Rich Domain Models, `ChatDomain` і `UserDomain` — мають методи для контрольованих мутацій стану.

## 2. Які переваги дало розділення на шари?

**Єдина відповідальність.** Кожен файл виконує одну роль: контролер лише приймає HTTP-запит і делегує, сервіс лише оркеструє, фабрика лише валідує, репозиторій лише персистує, domain-клас містить бізнес-поведінку. Знайти де відбувається конкретна дія — тривіально.

**Незалежна перевірка інваріантів.** Фабрики — чистий TypeScript без жодного імпорту з NestJS чи TypeORM. Їх можна тестувати без підняття бази даних або DI-контейнера:
```typescript
expect(() => UserFactory.create({ email: 'bad', ... })).toThrow(InvalidUserDataError);
```

**Централізована обробка помилок.** `DomainExceptionFilter` в одному місці перетворює будь-який `DomainError` на відповідь із потрібним HTTP-статусом. Сервіси більше не знають про HTTP.

**Рольова модель як перший клас.** `MemberGuard` з `@RequiresPermission()` декоратором дозволяє декларативно захищати маршрути. Додати нове право до ендпоінта — один рядок коду.

**Поведінка на домені.** `MemberDomain.hasPermission()`, `ban()`, `canActOn()` тощо живуть де і має бути — на самому об'єкті. Сервіс лише оркеструє: перевіряє передумови, викликає метод домену, зберігає результат.

**Тестованість.** Кожен шар тестується ізольовано. Domain-клас тестується без жодних моків. Сервіс тестується з mock-репозиторієм. Guard — з mock-рефлектором.

## 3. Які недоліки та ускладнення з'явилися?

**Більше файлів і коду.** Один модуль `message` тепер складається з 8+ файлів (`entity`, `domain`, `repository/`, `service`, `controller`, `module`, `dto`, `errors`, `factory`) замість 3. Для невеликого проєкту це відчутне збільшення обсягу коду без пропорційного приросту функціональності.

**Складніша навігація.** Щоб простежити один запит від HTTP до бази даних, потрібно пройти через контролер → guard → сервіс → domain-метод → репозиторій → entity mapper → TypeORM → фільтр помилок. Для нового розробника поріг входження вищий.

**Маппінг між шарами.** Entity → Domain відбувається у приватному `toDomain()` репозиторію. При змінах полів entity потрібно оновити і mapper. Якщо entity і domain розходяться суттєво, маппінг стає нетривіальним.

**Відсутність інтерфейсів репозиторіїв.** Поточні репозиторії — конкретні класи, а не реалізації інтерфейсу (`IChatRepository`). Це означає, що сервіс технічно залежить від конкретного класу, а не від абстракції. Для повної ізоляції варто ввести інтерфейси.

## 4. Наскільки простіше тепер змінити БД або фреймворк?

**Зміна бази даних** стала суттєво простішою порівняно з попереднім підходом. Вся робота з TypeORM зосереджена у двох місцях: entity-файли та `*Repository`-класи. Фабрики, доменні класи, сервіси та контролери не мають жодної залежності від конкретної СУБД.

Щоб перейти, наприклад, на MongoDB, потрібно:
1. Замінити entity на MongoDB-схеми
2. Переписати методи `*Repository` під новий ORM
3. Залишити решту коду незмінною

Якби були реалізовані **інтерфейси репозиторіїв** (`IChatRepository` тощо), заміна зводилась би лише до нової реалізації без будь-яких змін у сервісах — поточна архітектура на 90% до цього готова.

**Зміна фреймворку** складніша, оскільки сервіси залежать від `@Injectable()` та NestJS DI. Однак весь доменний шар (фабрики, domain-класи, помилки) повністю портабельний — це чистий TypeScript. Контролери, guards і фільтри специфічні для NestJS і потребували б переписування, але бізнес-логіка залишилась би незмінною.

## 5. Rich Domain Model vs Anemic: як ми підходили до вибору

У проєкті використовується **змішаний підхід**: для частини модулів — Rich Domain Model, для інших — Anemic з обґрунтованих причин.

### Де обрали Rich Domain Model

**`MemberDomain`** — найбільш очевидний кандидат. Об'єкт має складну поведінку: перевірку прав (`hasPermission`), ієрархію ролей (`canActOn`), стан членства (`isBanned`, `hasLeft`, `isActive`) і контрольовані мутації цього стану (`ban`, `unban`, `leave`, `setRole`). Розміщення цієї логіки у сервісі призводило б до того, що сервіс знає занадто багато про внутрішній устрій учасника. Тепер сервіс просто викликає `requesting.hasPermission(...)` або `target.ban()`.

**`MessageDomain`** — має осмислені предикати стану (`isDeleted`, `isOwnedBy`) і бізнес-операцію (`delete`). Без цього у сервісі з'являлися б прямі порівняння полів: `message.deletedAt !== null`, `message.memberId === requesting.id`. Метод `delete()` інкапсулює той факт, що "видалення" означає "встановлення `deletedAt`", а не справжнє видалення рядка.

**`UserDomain`** — має контрольовані переходи стану: верифікація email (`verifyEmail()` — встановлює `emailVerified = true` і очищає OTP одночасно), керування OTP (`setOtp`, `clearOtp`), зміна пароля. Ці операції — не просто встановлення поля, а бізнес-переходи зі своїми інваріантами.

### Де залишили Anemic (з методами для мутацій)

**`ChatDomain`** — має лише один вид мутації: оновлення `name` та `description`. Метод `updateInfo()` тут виконує роль контрольованої точки зміни, але не містить складної логіки. Повністю Anemic тут теж прийнятно — вибір зроблено на користь консистентності з іншими domain-класами.

### Загальний принцип

Rich Domain Model доречна коли:
- Об'єкт має складний внутрішній стан із переходами
- Існують бізнес-правила, специфічні для самого об'єкта (не для оркестрації між об'єктами)
- Без методів сервіс змушений "заглядати всередину" об'єкта

Anemic прийнятна коли:
- Об'єкт — переважно контейнер даних без власних інваріантів
- Логіка стосується взаємодії між кількома об'єктами (це відповідальність сервісу)
- Додавання методів виглядає як "примусове" збагачення без реальної цінності
